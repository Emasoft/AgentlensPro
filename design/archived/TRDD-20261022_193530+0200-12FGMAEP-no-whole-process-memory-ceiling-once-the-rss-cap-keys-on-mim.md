# No whole-process memory ceiling once the RSS cap keys on mimalloc commit

Step 4 of TRDD-2HRA270Y moves the hard cap from phys_footprint to mimalloc committed bytes (owner 2026-10-22, DuckDB may exceed 2 GB). DuckDB allocates through system malloc and was measured overrunning its own memory_limit (512MB limit gave 1150 MiB RSS; 1536MB gave 2497 MiB). With the cap on commit, a DuckDB runaway grows until jetsam kills the process and leaves no culprit log. Needed: a footprint backstop well above 2 GB that writes the same culprit log (or a logged warning threshold). The threshold value is the owner's call; record it here when given. Review finding from the step-4 adversarial review, 2026-10-22. 2026-10-22 clone run 1 (docs_dev/20261022-clone-run-report.md): the 2-second RSS sampler peaked at 4701 MB before it stopped at 900 s, while the composition lines show process RSS up to 5362 MB at uptime 1419 s and mimalloc commit peaking at 1873 MB; about 3.5 GB of process RSS sat outside mimalloc commit at that line, and the report does not measure which region holds it. This is deploy-gating: the step-4 guard counts only mimalloc and would not have stopped it. The run's DuckDB memory_limit is not recorded in the report, so the 512/1536 MB overrun ratios above do not apply to this figure.

## Design 2026-11-18

- 2026-11-18T06:32:58+0100 DECISION (main agent, under the owner delegation recorded in the Decision section): a whole-process footprint backstop is added to the memory guard of alcore. It exits with a culprit log, like the commit cap. Value: default = 3 x the commit cap (6144 MB at the default 2048 MB), lowered to half of the physical memory of the host when that is known, is smaller, and is still above the commit cap. Basis of 3 x: the commit cap 2048 MB plus one DuckDB instance at a 1536 MB limit with the overrun measured in the body of this card (2497 MiB) is about 4545 MB; the highest footprint in the two run reports read by the main agent is 3132 MB (docs_dev/20261023-prodcap-run-report.md line 34). Known weakness: docs_dev/20261022-clone-run-report.md took footprints only at 30, 150 and 290 s (1455, 1283, 1499 MB, peak 1588 MB) and none later, when process RSS reached 5362 MB; a production footprint with collection and log scan on has never been measured. If a healthy server exceeds the default, the log names the split and AGENTLENS_FOOTPRINT_BACKSTOP_MB raises it.
- 2026-11-18T06:32:58+0100 CODE (rust-core/crates/agentlens-core). (1) src/rss_guard.rs: pub fn resolve_footprint_backstop(raw: Option<&str>, cap_bytes: u64, total_memory_bytes: u64) -> u64, pure: an override in MB that parses, is positive and is above cap_bytes wins; otherwise 3 x cap_bytes (saturating), lowered to total_memory_bytes / 2 when total_memory_bytes > 0 and that half is below 3 x cap_bytes and above cap_bytes. pub fn footprint_backstop_bytes(cap_bytes: u64) -> u64 reads AGENTLENS_FOOTPRINT_BACKSTOP_MB and crate::server_stats::total_memory_bytes(). (2) pub fn enforce_footprint_backstop_with(read_footprint: impl FnOnce() -> Option<u64>, backstop_bytes: u64, commit_bytes: u64, flush_before_exit: impl FnOnce(), log_path: &Path, snapshot: &CulpritSnapshot): a footprint of None, or one at or under backstop_bytes, returns (inclusive boundary, like the cap); above it: flush, append to the same log file, print to stderr, std::process::exit(1). First line: alcore: FOOTPRINT BACKSTOP — phys_footprint N MB > backstop M MB, exiting (mimalloc commit C MB is under the cap K MB; outside mimalloc commit: N minus C MB); then the same counter lines as the commit-cap diagnostic, each with the prefix FOOTPRINT BACKSTOP. (3) check_and_enforce reads mi_commit_bytes once; above the cap it calls check_and_enforce_with with that value (the path of today); otherwise it calls enforce_footprint_backstop_with(phys_footprint_bytes, footprint_backstop_bytes(snapshot.cap_bytes), commit, ...). check_and_enforce_with keeps its signature and body; every existing test and the existing diagnostic text stay unchanged. (4) pub fn describe_limits() -> String: one line with the effective commit cap and backstop in MB and whether the footprint can be read on this platform; bin/alcore.rs prints it once at boot. (5) The header of rss_guard.rs and the comment above the call in prune_window (src/lib.rs) say that the backstop exists and why. (6) CHANGELOG.md: one line in the unreleased section.
