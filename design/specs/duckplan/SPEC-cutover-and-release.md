# Cutover and release of the DuckDB-index alcore

Marks: VERIFIED = read or measured in the cited file or command. INFERRED = derived here, not measured. OPEN = undecided, needs the owner or a measurement before it is relied on. OPEN (pending R2/E7) = the decision log's revision 2 and experiment E7 will settle it; nothing below may be built on it before then. Citations: DEC D-xx = decision id of the decision log, R1-xx = id of its revision 1, GC/EH/LI/IS = section or item id of the sibling spec, CF Hn = hazard, DEP1/DEP2 = the two card-reuse deploy reports, CL = repo CLAUDE.md. Ids of the form D1 to D12 without a prefix are CONTRACT-DELTA row ids (OCAT section 4; EH I18, I141-I145), a different namespace from DEC D-xx.

Rationale in one sentence: the owner decided "cutover all at once" (DEC header), so the new engine replaces the old one in a single switch, built and proven beforehand in an isolated shadow instance, with a rehearsed rollback that needs nothing from the new engine and an automatic trigger set during the first hour.

Terms: OLD = the current alcore (cards.duckdb, snapshot+delta sidecars, in-RAM summary). NEW = the DuckDB-index alcore: `index.duckdb` plus raw-line storage whose backend is OPEN until the Rust bench decides it (R1-D1: DuckDB-resident zstd column D, Parquet parts via DuckDB COPY C1, or Parquet parts via the Rust crate C2; DEC D-4 was replaced by R1-D4, D-10 by R1-D10). Wherever this spec says "parts" it means the Parquet part files of backend C1/C2 and the directory is ABSENT under backend D. LIVE data dir = `~/.agentlens` (VERIFIED listing 19:45, section 4.2). SHADOW = an isolated NEW instance with its own data dir.

## 0. Principles (each traced to a decision)

1. One binary. The sha256 of the binary that passes the gates (section 2) is the binary that runs the shadow soak, the golden capture, the switch and the release candidate build. Any rebuild restarts the gates that depend on the binary (G3, G8, G9, G10, G11, G15). Source: GC A10 (manifest names the build under test).
2. The index is never auto-deleted (DEC D-11, CF H1): every step below that touches `index.duckdb` moves aside, never removes, and a failed open exits naming the holder. Because plain fsync does not survive power loss (DEC D-ENG-6) the index is also never the only copy of anything without the recovery set of R1-ENG6 (section 1.6, G15).
3. Nothing of OLD is touched by NEW (EH I94, I147; LI section 7). The cutover is reversible exactly as long as OLD's own files are byte-identical to their state at OLD's last stop (checked by rollback step R5, section 4.4, against the ownership table of section 4.2).
4. Fail fast: a gate is a command with a pass criterion; there is no "looks fine". A gate that cannot be run is a blocker, not a skip.
5. The machine stays responsive (DEC header): LIVE producers keep normal QoS, only the BACKFILL runs at background QoS (R1-D7), under a measured CPU budget and a governor (section 1.3).
6. Disk is the owner's to free (global rule). The disk is 96% full (VERIFIED `df -h /`: 1.9 TB, 75 GiB available at 19:45). Every phase has an exact free-space floor and a stated action when it is crossed (section 1.4); below a floor STOP and ask, never delete to reclaim space.
7. The raw storage backend is decided before anything is built on it (R1-D1): gate G0 precedes the shadow build, because the backend fixes the on-disk layout, the size projection constant K, the snapshot cost and the relative-path requirement R-S2.
8. The memory budget must close before the switch (R1-BUDGET): the startup budget check requires the 4,096 MiB cap or a smaller measured sum (gate G16). IS D-13 (the 4096 default in `alcoreSpawnEnv`) is a PLAN, not a fact (R1-D13): VERIFIED by grep that `AGENTLENS_RSS_HARD_CAP_MB` does not appear in `src/cli/serverControl.ts` at HEAD, so it has not landed.

## 1. Shadow build

### 1.1 What the shadow is

NEW started by hand (not through hook revive) with its own `DATA_DIR`, its own three ports, and `AGENTLENS_STARTED_BY=cutover-shadow` (provenance stamp, GC 1.4). It builds the full index by backfilling the real corpus while OLD keeps serving on 3000/4316/4318. It is a normal NEW instance; the only special thing is that it must not write anywhere outside its own data dir and must not bind any live port.

Location (DECIDED, was OPEN): `$SHADOW=~/Code/AgentlensPro/reports_dev/shadow/data`, a visible, gitignored, never-deleted `_dev` folder (not a new dot folder). The same-volume requirement is VERIFIED: `/usr/bin/stat -f %d` returns 16777229 for `~/.agentlens`, `~/.claude/projects` and `~/Code/AgentlensPro/reports_dev`. Use the absolute `/usr/bin/stat`: the `stat` on PATH is GNU coreutils, where `-f` means "filesystem status" and `%d` is not the device number (memory page gnu-coreutils-shadows-bsd-tools-on-path), so the old command text `stat -f %d` would have produced a false pass or an error. The file names inside `$SHADOW` (index file, parts directory) are OPEN until the storage spec fixes them.

### 1.2 Source choice: read the live corpus read-only, do not clone it

Options compared:

| option | how | verdict | reason |
|---|---|---|---|
| A. APFS clone of the corpus (`cp -c -p -R`, as GC 2.1) | shadow reads a frozen copy | REJECTED for the shadow that will be switched in | file identity is `(dev, inode)` (R1-D5: node identity is the inode, path an updatable attribute) plus fingerprint (CF H6); every clone file has a new inode, so after the rename into the live data dir every live transcript would look like a rotated/new file and be re-read from 0 (duplicates or wasted backfill). Also the shadow would be as old as the clone and still need catch-up. A is the right choice for the GOLDEN instance (GC), not for the shadow. |
| B. Read live `~/.claude/projects` and live spans read-only, by their real paths | shadow `file` rows carry real `(dev, inode, path)` | CHOSEN | the index that is renamed into the live data dir already describes the live files, so the switch needs only a catch-up of the bytes appended since (section 3.8). 18.72 GB / 27.7k files read, no extra disk for the corpus (DEC D-DAT-8). |

Requirements this puts on NEW (each is an implementation requirement for the owner of the reader/ingest spec, OPEN until confirmed in code, because `bin/alcore.rs` was not read for this spec, same caveat as GC section 9):
- R-S1 shadow mode (name INFERRED: env `AGENTLENS_SHADOW_BUILD=1`, accepted only together with an explicit `DATA_DIR` different from the default) in which the process (a) opens transcript roots and the live `spans/` directory read-only (no create, no rename, no delete there), (b) binds no OTLP listener on 4318 (a busy 4318 refuses to start by design, CL "Ports"; the shadow gets a free OTLP port nobody posts to, and ingests spans only by tailing the live span NDJSON, DEC D-6 as corrected by R1-D6), (c) never writes hook-events, statusline, account-state, body store or config under the live data dir, (d) refuses to start if `DATA_DIR` equals the live data dir.
- R-S2 every path stored in the index that lives under the data dir (Parquet part files under backends C1/C2, temp, spill, snapshots) is stored RELATIVE to the data dir, so `mv` of the index plus parts directory into another data dir keeps working. Transcript and span paths are absolute (they are outside the data dir). Test: move a small shadow data dir to a new name and open it (part of G11).
- R-S3 identity tolerates the move: `file` is keyed by `(dev, inode)`; the shadow and the live data dir are on the same volume (VERIFIED, 1.1), so `dev` is equal.
- R-S4 thread QoS is set per thread by NEW itself (section 1.3): the shadow is started at NORMAL process priority.

Proof that the shadow touched nothing outside `$SHADOW`, strongest first:
1. Enforcement, not audit: start the shadow under `sandbox-exec` with a profile that denies `file-write*` for the subpaths `~/.agentlens` and `~/.claude` and allows writes only under `$SHADOW` and the shadow's temp directory (set `TMPDIR` and the DuckDB `temp_directory` inside `$SHADOW`). `/usr/bin/sandbox-exec` exists (VERIFIED `which`); that it is deprecated but still functional on this macOS, and that DuckDB and the allocator run inside the profile, is INFERRED and is tested first in G11 (a deliberate write into `~/.agentlens` from a probe process under the same profile must fail with EPERM). A shadow that tries to write outside then FAILS LOUDLY instead of silently writing. Reads stay allowed (transcripts, spans).
2. Audit when root is available: run once under `/usr/bin/fs_usage -w -f filesys <pid>` for 10 minutes in the rehearsal (G11) and grep the log for `write|rename|unlink|open.*O_CREAT` against paths outside `$SHADOW`: zero hits required. `fs_usage` needs root (INFERRED); where root is unavailable this audit does not run.
3. Weakest, labelled as weaker: before the shadow starts record a manifest (path, size, mtime, sha256 for files under 100 MB) of every file in the live data dir and of `~/.claude/settings.json` and `~/.claude.json`; transcripts legitimately grow, so for them no manifest is taken (`find ~/.claude/projects -newer` is NOT used). After 24 h the manifest must differ only by OLD's own known writes (section 4.2 ownership table).

### 1.4 Preconditions and floors (STOP and ask below any floor)

Preconditions:
1. Same volume: `/usr/bin/stat -f %d ~/.agentlens`, `$SHADOW` and `~/.claude/projects` all equal (VERIFIED 16777229 for the three existing paths; `$SHADOW` is re-checked after creation).
2. Gate G0 passed (raw backend decided and frozen) and gate G16 passed (memory budget closes against the cap that will be used).
3. OLD is up and its totals are being sampled (section 2, G3 band).
4. The binary under test is the release-profile build, signed (`codesign -s - --force`, CL), `--version` exits 64 with usage text, not 137 (VERIFIED as the check used in DEP1: "alcore --version exit 64 (usage text; not 137, codesign ok)").
5. All of the shadow's boot checks pass: json and parquet features present with `autoinstall_known_extensions=false; autoload_known_extensions=false` so a missing feature fails at startup, never at runtime (DEC D-ENG-1). R1-ENG1 order: the static features are enabled first, every other DuckDB instance in the process (transcript_sql `read_ndjson_auto`, the bodies store Parquet COPY) is verified with autoload off, and only then is autoload turned off; the boot check covers all instances, not only the index.

Free-space floors. Unit: GiB as `df -k /` reports in the Available column divided by 1,048,576 (now 19,527,719 blocks of 4 KiB = 74.5 GiB). Index size per backend from the measured constants K of D-1 and R1-D1 (GB per GB of raw, index plus parts): C1 0.128, C2 0.138, D 0.22, so for the 18.72 GB corpus 2.40, 2.58 and 4.12 GB, plus the 0.94 GB of spill files (DEC D-2) as an upper bound, giving at most 3.4, 3.5 and 5.1 GB per NEW data dir (derived, INFERRED: DuckDB temp and WAL are not measured). Snapshots clone the DB file and Parquet parts clone for free, but a DB-file clone diverges after later checkpoints up to about 1x the DB each (coordinator note, pending R2/E7), so three rotating snapshots cost at most 3x the DB file: under D that is 15.3 GB, under C1/C2 a fraction of it (the DB file is small, not measured).

| floor | value | what is checked / what happens when crossed |
|---|---|---|
| F-START | 40 GiB (55 GiB if the backend is D) | free space before ANY phase that creates a NEW data dir: the shadow, the golden NEW instance (G3, a second full index), the G12 stranger copy, the G11 rehearsal scratch dir. Nothing is deleted to reclaim space (global rule; only `/tmp` is exempt) |

| F-SNAP | 20 GiB + DB-file bytes | before each rotating snapshot; below it the snapshot is skipped AND flagged (never silently), the flag stays until the next successful snapshot |

Retirement (section 7) moves files on one volume and needs no space.

### 1.5 Running and completing the backfill

1. Start: the detached launcher (`scripts_dev/detach-run.py`, VERIFIED path; a background task killed by compaction otherwise: memory page "Detach long jobs from session lifecycle") runs `<alcore> serve` under `sandbox-exec` (1.2) with the env of 1.1 under `env -i` plus an explicit list (as GC 2.3), at normal priority (1.3), and records pid and start time in `$SHADOW/shadow.pid.txt`.
2. Completion = all of: `file.offset == size` for every file that is not currently growing (mtime older than 5 min), and for growing files lag under 60 s; `backfill.complete == true` in the aggregate envelope (CF H18 requires `{complete, backfill:{files_done, files_total, bytes_done}}` on every aggregate response, so the shadow can say it); `ingest_batch` stops producing BACKFILL-lane batches for 3 consecutive 60 s samples.
3. Backfill ordering caveat (CF H18): newest-mtime-first answers the 5 h / 7 d windows early but lifetime totals only at the end; no gate that compares totals may run before completion.
4. Then the shadow runs the one-shot legacy import on a PROVISIONAL freeze of the four sidecars (section 3.4 describes the exact copy and why it is provisional): this puts the legacy rows into the shadow so that G5, G6, G7 and G8 measure the final shape of the index.
5. Then the shadow KEEPS RUNNING in live-tail mode (it follows new bytes of the corpus and spans) through the gates G4 to G8. It is the same process the soak measures.

### 1.6 Recovery set (R1-ENG6, extends DEC D-ENG-6)

Why: after cutover the index plus raw storage is the ONLY copy of transcripts Claude Code later deletes and of the 5,742 legacy cards, and fsync here does not flush the drive cache, so a power loss can reorder writes and corrupt the file. Required of NEW, each proven in G15:
1. A rotating backup set (keep 3; one daily, one after the backfill completes, one just before the switch) made by CHECKPOINT then an APFS clone of the index (and parts) into `<dataDir>/index-snapshots/`. The snapshot PROCEDURE and its disk cost are OPEN (pending R2/E7): the working assumption is that a clone is taken only with the writer paused after CHECKPOINT, DB file and WAL together, that Parquet parts clone for free and DB-file clones diverge up to about 1x the DB each.
2. The legacy cards are exported once to an immutable NDJSON file `<dataDir>/legacy-export/legacy-cards-<utc-stamp>.ndjson` (mode 0444, sha256 in its manifest), written at the switch (section 3.4) before the index is opened live. It is the third independent copy besides `legacy_card` and `legacy-source/`.
3. A reindex path `alcore reindex --from-raw` (name OPEN) that rebuilds the derived tables from the raw storage into a side database, subject to F-REINDEX.
4. A startup integrity check that, on a failed integrity check, moves the file aside (`index.duckdb.corrupt-<utc-stamp>`, DEC D-11) and falls back to the NEWEST snapshot plus a re-ingest from that snapshot's stored offsets, never to an empty database.

## 2. Gates before the switch

### 2.0 Schedule: one heavy job at a time

Heavy jobs: `cargo build --release` and `cargo test --workspace` (G1, G2); the golden captures of OLD and NEW including NEW's own full backfill from the clone (G3, G9); the stranger first boot with a full backfill (G12); the shadow backfill (1.5). Light jobs: a shadow in live-tail mode, its read-only checks (G4 to G7), the G8 sampler, G15, the G11 rehearsal (it starts from a 12 h old clone of the shadow index, so its catch-up is small). The previous text had both "do not run the shadow while another full-corpus job runs" and "G8 runs concurrently with G3 to G7", which could not both hold, and G3/G12 each need a full backfill of their own. Order: G0, G16 (decisions and budget) then G1, G2 then G3 and G9 (golden, hours) then G12 then the shadow backfill; then G4 to G8 with G11 and G15 started inside the G8 closed window (hour 12, see G8); then G10, G13, G14. Any binary change (G1 hash change) restarts from G3 on.

### 3.8 Catch-up of data that arrived during the switch (offsets make it automatic: the proof)

What arrives between the shadow stop (3.2) and NEW's first scan (3.6): (a) transcript lines appended by Claude Code sessions (about 36 live sessions), (b) OTLP spans POSTed to 4318 (OLD is down, so the POST fails), (c) hook events and statusline samples.

(a) Transcripts. Argument, each premise from the decisions: transcripts are append-only in practice (DEC D-DAT-1: 27,763 offsets <= size over 27 min); every batch commit writes the rows AND the new per-file `offset` in ONE transaction guarded by compare-and-set (`UPDATE file SET offset=:new WHERE file_id AND offset=:expected AND gen`, row count 1, DEC D-ENG-5, D-8, CF H3), so on disk the pair (rows, offset) is never torn; on start the scheduler lists files and reads `[offset, size)` of each file, identity checked by `(dev, inode)` plus head fingerprint plus newline-at-offset (DEC D-DAT-1, CF H6, R1-D5); a file whose identity changed is a rotation and ingests the new generation as new rows (R1-D4(b): the old generation stays in the archive and is hidden by `gen = file.gen`, and that node's rollup is recomputed from current-generation rows; OPEN pending R2/E7). Therefore the bytes appended during the gap are read exactly once after the start, and the bytes before the gap are not re-read. The index file written by the shadow and the live files share `(dev, inode)` because the shadow read the live paths (section 1.2): this is the reason the shadow does not read a clone.
