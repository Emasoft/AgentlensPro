**DONE — Gap D: the risk does NOT materialize, and the truncation that IS happening has a different
producer, a different limit, and no consequence.** Measured over **713,853 spans** in the heaviest
segment plus 12,071 in the newest:

- **Claude Code never truncates in our data.** The knob `CLAUDE_CODE_OTEL_CONTENT_MAX_LENGTH` is set
  nowhere (not the env, not `~/.claude/settings.json`, not our code), and the largest string
  attribute on any span is `arguments` at **51,355** chars — under the 60,000 ceiling, though within
  15% of it, so this is worth re-measuring if content volumes grow.
- **Codex DOES truncate, at ~2 KB, and says so.** 212 of 573 large `output` values sit at EXACTLY
  **2,086** chars — which is also that attribute's maximum. A mass of values at one exact length that
  equals the max is a ceiling, not a coincidence, and the tail confirms it verbatim:
  `[... telemetry preview truncated ...]` on `codex.tool_result` spans.

**Why it is harmless, traced rather than assumed:** the only consumer is
`src/summarizers/codex.ts:150`, and `resultText` flows to exactly two places —
`resultSummary` (a human summary) and `fullResult` (display). **Nothing measures its length, derives
a byte count, or computes a cost from it**, so there is no number anywhere that a truncated string
makes wrong. The explicit marker also means a reader sees the truncation rather than being misled.

The one imprecision worth knowing: a field named `fullResult` can be not-full. It carries the marker,
so it is self-documenting rather than deceptive — not worth a rename on its own.

**The one genuinely new thing, and it is small:** `client_request_id` is a **UUID**, `request_id` is

id, different `request_id`), which `request_id` alone cannot do. Not needed by anything today.

The two detectors are **near-disjoint**: every real effort change happened in a session with no

The changes came from something that types no command — a `/model` switch (the session I traced by

**Rare AND invisible is the combination worth a detector**, since an effort change is a real
cold-write cause nothing else here can name.

Shipped as a standalone transcript scanner — gap A's proven shape: no card field, no DB column, no
ingest coupling, retroactive over all history.

**Four ways it could invent a transition that never happened, each closed and each pinned:**
- **ABSENT is not a value.** Only an EXPLICIT string `effort` is an observation, so the pre-2.1.212
  absent→present step is the FIELD APPEARING, not a change. Otherwise it manufactures one false
  break per session at the upgrade boundary, across all history. This is the rule
  `cacheBreakTimeline` already applies to `EFFORT_PARAM_CHANGED` — consistency, not invention.
- **SIDECHAIN records are partitioned out.** A subagent runs at its own effort and its records
  interleave into the parent's transcript; a naive difference reports two transitions per subagent
  (in and out) that nobody caused. Measured 0 sidechain transitions on this corpus — the guard costs
  nothing today and prevents a whole class of false culprit.
- **The FIRST observation in a partition is a BASELINE and emits nothing** — the same rule
  TRDD-H693VQLU landed on the same day, from the opposite direction.
- **Differencing is in TIME order, not read order** (one session can span several transcript files),
  and the filters run AFTER differencing, so dropping records can never difference across a hole.

**Corroborated by two independent implementations:** a throwaway Python probe and the shipped
TypeScript scanner agree, including the exact `xhigh→low→xhigh` pair in session `65af6f9e`.

## Deliberately out of scope, with the reason

- **`message_delta` cumulative double-count (CC 2.1.214).** We consume aggregated OTEL and parsed
  transcripts, never raw stream frames, so the double-count cannot reach us.
- **Prometheus `# UNIT` lines, Azure chunked-encoding rejection, `TRACEPARENT` trace_id.** Exporter-
  side fixes in Claude Code; nothing for a receiver to change.
- **`/fork`, `/subtask`, `/branch`, `/resume` as cache-risk commands.** Their cost lands in a
  DIFFERENT context than the session the command was typed in, so billing them to the parent's next
  turn would be a wrong number. If they are ever wanted, model them as session-SPAWN events with the
  child's cold start as the cost. Pinned by a test.
- Every Windows / PowerShell / worktree / agent-view / UI fix in the range.
