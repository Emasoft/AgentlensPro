## Context — why (the 2026-07-10 incident, measured)

A 5h window drained in ~30min. Measured culprits: PREMIUM_MODEL_FANOUT (73.4M input-equiv),
FORK_STORM (66 full-prefix cache writes, worst 565k tokens with cache_read=0 — forks of a fat
parent into a TTL-expired cache), plus a cold resume right after a rate-limit stall.
`investigate_burn` (TW14MO7A) explains a drain after the fact; `check_burn_risk`/`--guard`
(W6UH8LPA) warns if the agent armed a monitor. **Neither can PREVENT anything, and neither
detects the every-turn cache-invalidation pattern** (the lean-ctx strip-in-place class: big
`cache_creation` with ~zero `cache_read` on call after call).

## What ships

### 1. CACHE_THRASH detection (the "invalidating most of the cache every turn" signal)
`src/bodiesActivity.ts` — `BodiesActivityTracker`. Response bodies land as files in
`~/.agentlens/otel-bodies` the moment calls complete and carry Anthropic's EXACT
`usage.cache_creation_input_tokens` / `cache_read_input_tokens` + `model`. The tracker does an
**incremental** scan (readdir + stat ONLY unseen names — bodies are write-once, so an old name
can never become new) and keeps two rolling rings:
- **response-usage ring** → `CACHE_THRASH`: ≥3 responses inside 5min with
  `cache_creation > 100k` AND `cache_read < 25%` of (creation+read) — i.e. most of the prefix
  is re-WRITTEN, not read, repeatedly. Detail names the model + tokens re-billed.
- **large-request ring** → feeds `HUGE_REQUEST_BURST` without the previous full
  readdir+stat-every-file pass (that pass stats ~22k files on a hot dir; the ring stats only
  new ones).

### 2. The agent-launch gate (PREVENTION — PreToolUse on `Agent|Task|Workflow` ONLY)
`scripts/spy-agentlens-gate.sh` (curl-only, no node spawn) + `POST /api/agent-gate` +
`src/agentGate.ts` (pure `evaluateAgentGate`, unit-testable). The hook forwards the PreToolUse
payload; the resident server decides in <20ms from in-memory state + ONE transcript-tail read:

- Parent context size = REAL tokens from the last `message.usage` in the transcript tail
  (256KB read), not a bytes/4 guess. Cache warmth = transcript mtime vs the 5-min TTL.
- **DENY** (high-confidence disaster, reason fed back to the model so it can adapt):
  1. CACHE_THRASH active → "recent calls re-write ~Nk tokens of prefix per turn; more agents
     multiply it — fix the thrash source first".
  2. StopFailure ≤10min AND ≥1 SubagentStart already in last 2min → "cold resume: one warm-up
     agent is already in flight, wait for it" (the FIRST launch after a stall is ALLOWED —
     that IS the warm-up; mechanically enforces the incident lesson).
  3. ≥8 SubagentStarts in 60s → runaway fan-out, "let the wave settle".
  4. fork-type launch AND parent ≥200k tokens AND cache cold AND ≥2 launches in 2min →
     fork storm forming.
- **WARN** (systemMessage to the user; never blocks): fat-parent fork while warm; first cold
  fork (names the tokens it will re-pay); ≥5 starts/2min heads-up incl. "pin a cheap model"
  when the recent-response ring shows premium traffic and `tool_input.model` is unset.
- **ALLOW**: empty 204 → hook prints nothing.

Not-disruptive guarantees: fires ONLY on agent-launch tools (rare calls, never per-tool);
fail-open on server-down/timeout/parse-error (hook always `exit 0`; curl `--max-time 2`);
kill-switch `AGENTLENS_GATE=off` checked in-script before any network; downgrade mode
`AGENTLENS_GATE_MODE=warn` turns every deny into a warn. Thresholds env-tunable
(`AGENTLENS_GATE_*`).

### 3. The in-band advisor (notify the MODEL, deduped — PostToolUse on the same matcher)
Same script, same endpoint, `hook_event_name: PostToolUse` branch: when a risk episode
(CACHE_THRASH / FANOUT_BURST) is newly active as an agent wave completes, the server returns
`hookSpecificOutput.additionalContext` with ONE short warning; server-side dedupe = one
injection per risk episode per session per 10min. Rationale: PreToolUse deny-reason reaches
the model only on deny; `additionalContext` is the only supported in-band channel for a
non-blocking model warning. Injections are tail-appends (cache-safe) and RARE by construction
— the lean-ctx lesson (per-call injections later stripped in place = prefix rewrites, #778)
is why this is transition-gated, not per-call.

### 4. Performance (the "hooks must not slow the system" requirement)
- Hooks NEVER spawn node — bash+curl one-liners; the CLI is not on the hook path at all.
- Server hot path is resident state: **in-memory hook-event ring buffer** (fed by the POST
  handler, boot-seeded from the last 1h on disk) replaces per-check NDJSON reads;
  `BodiesActivityTracker` replaces per-check full-dir stats.
- Acceptance: measured `POST /api/agent-gate` p50 < 20ms; `check_burn_risk` p50 < 30ms on a
  hot bodies dir; gate hook end-to-end (bash+curl) < 60ms. Numbers recorded below.
- Rust helper + SQLite: deliberately NOT added unless the measurements fail the acceptance —
  verdict recorded below after measurement.

## Measured results (2026-07-10, live)

- `POST /api/agent-gate` (with a 51MB transcript in the payload → bounded 256KB tail read):
  **p50 0.9ms, p90 1.0ms, max 1.2ms** over 30 calls. Target was <20ms.
- Gate hook END-TO-END (bash + curl + server decision): **14ms**. Server down: fail-open in
  **13ms**. Kill-switch (`AGENTLENS_GATE=off`): 0 network, exit 0.
- CLI boot (node, usage path): **30ms**; interactive `check_burn_risk` round-trip (node boot +
  MCP session + tool): ~0.7s — irrelevant to hooks, which never spawn node.
- **Rust helper / SQLite verdict: NOT needed.** The hot path is one curl into resident memory
  + one bounded tail read — 20× under the acceptance target. Revisit only if a future feed
  forces per-call body parsing.
- Live deny verified end-to-end on an isolated instance: COLD_RESUME_FANOUT (with the incident
  numbers in the reason), RUNAWAY_FANOUT at 8 starts/60s, PostToolUse advisory injected once
  and deduped to 204 on repeat, allow = empty 204.
- `--install-hooks` wrote exactly the 2 gate entries (matcher `^(Task|Agent|Workflow)$`, sync,
  timeout 3), preserved the pre-existing foreign PostToolUse hook, verified transaction with
  backup. Lifecycle entries already current — untouched.
- Guard loop coverage: `runGuard` calls with `verbosity:'full'`, so all 6 risks (incl. the
  6th, CACHE_THRASH) survive the lean-shaper's 5-row array cap. Manual CLI calls see the cap
  with an explicit `_truncated` note — by design.
