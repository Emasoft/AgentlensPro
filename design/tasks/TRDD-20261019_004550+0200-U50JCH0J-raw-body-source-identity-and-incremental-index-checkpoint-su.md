# Raw-body source identity and incremental index checkpoint substrate

## WHY
The actively growing raw-body corpus needs stable source identity and restartable discovery before any byte can be migrated or safely removed; rescanning hundreds of thousands of files without a durable checkpoint is neither bounded nor auditable.

## Scope
- Define a collision-resistant source identity from canonical provenance and content evidence, independent of mutable path names.
- Build and maintain an append-safe incremental `index.jsonl` checkpoint substrate that discovers new and changed raw-body sources without a full rescan on every run.
- Persist enough source metadata to resume after interruption and to distinguish unchanged, replaced, truncated, and newly appended inputs.
- Make discovery idempotent and deterministic under concurrent corpus growth.

## Delivered
- Four new files: src/rawBodySourceIdentity.ts (the content-derived identity and the cheap fingerprint), src/rawBodySourceIndex.ts (the versioned append-only checkpoint format, its writer, and outstandingSources), src/rawBodyDiscovery.ts (the idempotent, restartable discovery pass), src/test/rawBodySourceIndex.test.ts (55 tests, real files in mkdtemp under os.tmpdir, no mocks).
- ENTRY POINT: outstandingSources(records, corpusPaths, alreadyMigratedPaths, passOutcome) in src/rawBodySourceIndex.ts — the function that decides what a later stage migrates. The checkpoint format version is 3 (source-index.v3.jsonl). Version 3 added the 'restored' reason - a body that came back supersedes its own 'gone' tombstone - so a version-2 log and a version-3 log differ in the reasons a record may carry, and a version-2 log is refused as a version, not converted. The bump is NOT optional: the validator checks the version PER RECORD and the writer stamps the current version on every record, so without it an older build would PASS the version check and then fail MID-FILE on the reason, with no version signal at all.
- The module headers point at the contract below rather than restating it, so the two cannot drift.
- The module header for outstandingSources states that a 'gone' TOMBSTONE IS AUTHORITATIVE and is never outstanding work, whatever the corpus set says - the restore is handled by the pass, which writes a 'restored' record carrying a freshly computed digest. The record reasons are discovered, content, replaced, refined, refused, retracted, restored, gone.

## Consumer contract
THE OUTSTANDING MIGRATION SET IS THE RESULT OF outstandingSources(records, corpusPaths, alreadyMigratedPaths) (src/rawBodySourceIndex.ts), AND NOTHING ELSE. A 'gone' TOMBSTONE IS AUTHORITATIVE AND IS EXCLUDED, whatever the corpus set says. The restore is handled by THE PASS, not here: when a body comes back the pass VISITS it, re-reads it, and writes a fresh record with reason 'restored' that SUPERSEDES the tombstone - and that record carries the CURRENT bytes' digest, freshly computed. So a source in the set never carries a tombstone's old digest. A tombstone survives only for a path the pass did NOT see, which is exactly where the corpus check cannot be trusted. A TOMBSTONE IS A STATEMENT ABOUT THE PAST AND IS SUPERSEDED ONLY BY A PASS: a body restored between two passes stays invisible until the next pass runs, so the caller MUST RUN THE PASS BEFORE ASKING FOR THE OUTSTANDING SET. THE WINDOW IS EXACTLY THE PASS'S OWN DURATION: the pass lists the corpus ONCE at its start, so a body restored AFTER that listing is not seen by THAT pass and stays invisible until the FOLLOWING one - the card's earlier phrasing understated this. A body that is present but UNREADABLE is a different case and is defensible: the pass could not produce identity evidence for it, so it has no record and no tombstone, and an absent record excludes nothing - unless it carried a tombstone from an EARLIER pass, in which case that stale tombstone stands and the body is excluded until it becomes readable. The window is one pass, not for ever - but it is a window, and a runner that skips the pass walks into it. AND THE PASS MUST HAVE BEEN COMPLETE: outstandingSources TAKES A REQUIRED `passOutcome` ARGUMENT and REFUSES to answer when it is false. A pass that stopped early (maxFiles) leaves tombstones standing for bodies it never reached, and since a tombstone is authoritative, a body that is PRESENT and UNMIGRATED would be excluded because the pass did not look at it - the set would have a hole in it, and the hole would be exactly the bodies the caller most needs. The argument is REQUIRED rather than optional on purpose: a default of true would let a caller who forgot to think about it get a silently incomplete answer, and the whole point is that the incomplete answer is never returned quietly. THE OUTCOME MUST BELONG TO THE PASS THAT PRODUCED THIS LOG. The outcome carries the pass's durable record count and the log carries its own, so the two are compared: the log must be AT LEAST as new as the pass that produced it. Pass the log's own count and a stale outcome - from an earlier pass, or from a different one - is caught mechanically. The likely mistake this prevents is the runner that runs the pass, does other work, and then asks with an outcome that is no longer current. The caller passes the PASS'S OWN OUTCOME OBJECT, not a bare boolean, so it cannot assert completeness it never checked - a boolean is not `{ complete: boolean }`, so the compiler stops `true`. WHAT THE GUARD DOES NOT PREVENT: a caller that CONSTRUCTS a fake outcome object. It protects against a mistake, not against a deliberate misstatement - the runner's own review prevents the latter, and the runner must be reviewed like everything else here. It applies every condition - still present in the corpus, latest reason is not 'gone', not refused by a partner that still exists, and a material class - so a consumer cannot forget one. Deriving the set by hand from the class field alone is WRONG: a 'gone' record carries class 'new' ('it was never migrated'), which is exactly the shape of a source that still needs migrating. The pass's own output (observedMaterial) is PER-PASS and is empty over an unchanged corpus: that is the idempotence property the acceptance criteria demand, and it means 'nothing CHANGED', NOT 'there is nothing to migrate'. The DURABLE LOG is the record of what has been discovered. The checkpoint deliberately carries no 'migrated' flag: migration execution is a sibling card's job (TRDD-IFOQAQYV), and this card cannot assert a migration it did not perform. Hence the caller's alreadyMigratedPaths - a set of PATHS, not identities (a mismatched key THROWS rather than silently matching nothing). The function is PATH-KEYED: it answers 'what does the corpus hold RIGHT NOW', and a rename neither duplicates nor loses a source (measured: the pass writes a record under the new path with the same identity). ONLY A SOURCE'S OWN LATEST RECORD SAYS IT IS CONTESTED - a partner's record naming a source is not evidence that the source is contested, because a reclaimed partner keeps its last record for ever.

## Validation evidence
- Gates: tsc -p tsconfig.test.json exit 0; tsc --noEmit exit 0; eslint on the four files exit 0; mocha over out/test/test/rawBodySourceIndex.test.js exit 0 with 58 passing and 0 failing.
- REAL CORPUS SLICE (criterion 5): a deterministic 120-file slice of the live corpus (every Nth name, 32.8 MB) plus its real index.jsonl were copied to /tmp and discovery was run over it: pass 1 scanned 120, recorded 120, material 120, refusals 0, class tally all 'new', corpus index read 22,230 rows with 0 skipped and rowsWithoutProvenance 0; pass 2 recorded 0 and material 0 (idempotence on real data, the log stayed at 120 records); the derived outstandingSources set was exactly 120; 0 records carried a bad digest and 0 named a missing path.
- NOTHING WAS WRITTEN TO ~/.agentlens - the slice was a COPY in /tmp and the checkpoint went to a fresh temp state dir.
- THE FOUR DEFECTS FOUND AND FIXED, each reproduced before fixing. The fourth was found AFTER the card was first judged complete, and it is the one worth remembering.
- (1) a CRASH-ON-WRITE - the validator enforced class 'replaced' implies reason 'replaced', but the material class is carried forward on an unchanged observation, so a replaced file that later gained a provenance row was refused on the way IN, the pass threw and the log became unappendable; the invariant is now one-directional (a reason implies a class, a class does not imply a reason).
- (2) THE 'gone' RECORD WAS WRITTEN TWICE - the cheap-path block ran per triggering live path, so two live sources both refusing a reclaimed one each appended a 'gone' record; the guard is now on the REASON (a vanished path's latest record already being 'gone'), and a vanished path's 'gone' record now carries refusal null because a collision needs BOTH paths to exist.
- (3) A STALE REFUSAL WITHHELD A SOURCE - outstandingSources excluded any source whose latest record carried a refusal of ANY kind, including one naming only vanished partners, so a live file was never migrated; it now excludes only a refusal naming a partner that IS in corpusPaths, the same rule the pass uses.
- (4) A RESTORED BODY STAYED INVISIBLE - a body reclaimed from the corpus and later RESTORED with the SAME BYTES, THE SAME INODE AND THE SAME MTIME (a `mv` back or a `cp -p` - the shape that reaches the cheap path; a restore with a fresh mtime never did, and was already handled) was classified 'unchanged' on the next pass, so NO record was written, its 'gone' tombstone stood, and outstandingSources excluded a body that was PRESENT and UNMIGRATED - permanently invisible, silently. THE FIX PUTS THE RESTORE IN THE PASS, WHERE IT BELONGS: a path whose prior record is a tombstone no longer short-circuits on the cheap path, so the pass VISITS the body, RE-READS it, and writes a fresh record with the NEW reason 'restored' - its own reason, because 'retracted' would claim a refusal was lifted (none was) and 'refined' would claim the identity moved (it did not). The record carries the CURRENT bytes' digest, freshly computed, so the tombstone's old digest never reaches the outstanding set. A tombstone therefore stays AUTHORITATIVE: it is excluded whatever the corpus set says, because a tombstone survives only for a path the pass did NOT see. The caller obligation is one line: RUN THE PASS BEFORE ASKING FOR THE OUTSTANDING SET. Fifteen review rounds had not found it, because they tested the CONTRACT as written and the contract never contemplated a file coming back: the corpus never restores a file in a fixture. The fix: a prior 'gone' tombstone no longer suppresses a record, and outstandingSources honours a 'gone' reason only when the path is NOT in the current corpus (the corpus is the ground truth about the present; the log is only a statement about the past). THE LESSON FOR THE NEXT STAGE: a contract is only as good as the states it contemplates, and a LIVE corpus has states a fixture does not.

- It declined to manufacture a finding. SCOPE OF THIS VERDICT: it reviewed outstandingSources AS IT WAS AT THE TIME - four conditions and no precondition. The function has since changed shape: it now takes a FIFTH argument and a PRECONDITION (the pass that produced the log must have been complete) and an identity check (the outcome must belong to this log). So 'the four conditions' above are the four EXCLUSIONS, and the precondition and the identity check are obligations on the caller that this verdict did NOT review. The later rounds reviewed those changes on their own; this verdict's scope is deliberately the function as it stood when it was written, not the function as it stands now.
- One accepted limitation: the loader cannot distinguish written-but-not-fsynced from durable after a crash, so a power loss can leave the last record unflushed. The consequence is bounded and safe, but ONLY for a consumer that reads the LATEST record per path: the next pass re-derives that source and re-appends it, and because the log is append-only that re-append is a SECOND record for the same path. It is idempotent AT THE CONSUMER (latestByPath and outstandingSources both collapse to the latest), not idempotent in the log. A consumer that reads any record rather than the latest will double-count that source. This is a CONTRACT dependency, and the contract is above.

## Handoff to TRDD-IFOQAQYV
EVERY ONE OF THESE WILL BITE, verified against the code:
- (1) THE MISMATCHED-KEY GUARD. alreadyMigratedPaths is PATHS, not identities, and the function REFUSES an identity in BOTH of its path-argument sets - corpusPaths and alreadyMigratedPaths. A wrong corpusPaths is the more dangerous of the two: every comparison misses, the outstanding set comes back EMPTY, and a migration over an empty set reports success and migrates nothing. A wrong alreadyMigratedPaths re-offers every migrated source, and the migration runs twice over the same body. The guard recognises an identity two ways: EXACT MEMBERSHIP in the identities the log knows - both the source identity (record.id) and the content digest (record.digest), which are DIFFERENT values for the same body, so a caller keying on either is caught - and, underneath, a SHAPE check (64 lowercase hex characters, no path separator, no extension) that catches an identity from a corpus this log has never seen. The shape check never fires on a real path: a corpus file may legitimately be named by its digest, and a path with a separator or an extension is always a path. The one wrong key that still matches nothing silently is one that is neither an identity the log knows nor 64-hex-shaped - a path from a different corpus, say.
- (2) observedMaterial is PER-PASS and is empty over an unchanged corpus - the runner must call outstandingSources against the LOG, never iterate the pass output. AND THE LOG MUST BE COMPLETE: outstandingSources takes a required `passOutcome` argument and throws when it is false, because a pass that stopped early leaves tombstones standing for bodies it never reached, and a body that is present and unmigrated would then be excluded for ever.
- (3) The log alone cannot tell outstanding from reclaimed - the runner must pass the CURRENT corpus path set; a path absent from the corpus is excluded, which is correct and also means a reclaimed body is never migrated.
- (4) A refused source is WITHHELD - the runner must handle a source never offered because a live partner contends it, and must not read 'not offered' as 'nothing to do' without checking the log.
- (5) The runner must NEVER write to the corpus dir - the checkpoint lives under a caller-supplied state dir, deliberately not in the corpus dir, because Claude Code writes its own index.jsonl there.
- (6) THE RUNNER MUST RE-VERIFY THE DIGEST IMMEDIATELY BEFORE UNLINKING, AND ABORT ON A MISMATCH. outstandingSources returns records carrying the content digest the pass computed at discovery time; the log's claim is that the file at that path held those bytes THEN. Between discovery and deletion the file may have been rewritten - the corpus is live and this very drain has already demonstrated re-emission (the store has a reclaimed_reemitted path and a 'stored ts != capture time' case, so re-emission is observed behaviour, not a hypothesis). A runner that deletes on the log's claim alone can delete a file whose bytes are not the ones that were digested. The alreadyMigratedPaths throw covers a wrong KEY loudly; nothing in the log covers a CHANGED FILE, so the runner must hash the file again before the unlink and abort the delete on a mismatch. THE RE-VERIFICATION IS STILL REQUIRED, for the reason the log cannot cover: the record's digest was computed when the source was LAST OBSERVED, and the corpus is live - a PATH REUSED for a different body (body A reclaimed at path P, body B later written at P) means the digest at P describes bytes that are no longer there. The re-verification is what turns a candidate into a fact, and it is part of the contract, not caution. NOTE WHAT THE SUBSTRATE DOES NOT LEAVE TO THE RUNNER: a 'gone' tombstone is AUTHORITATIVE and never offered, so a reclaimed body cannot be deleted by mistake, and a RESTORED body gets a fresh record with a freshly computed digest, so a source in the set never carries a tombstone's old digest.

## Acceptance criteria
- [x] Repeated discovery over an unchanged corpus emits no duplicate source identities or work.
- [x] A crash at every checkpoint boundary resumes without omitting or duplicating a source.
- [x] Changed, truncated, replaced, and newly created sources are classified deterministically.
- [x] Each checkpoint is durable before later migration stages may rely on it.
- [x] The index format is versioned, incrementally readable, and validated against a representative corpus slice.

## Failure and refusal conditions
- Refuse ambiguous identity collisions rather than choosing a source silently.
- Refuse malformed or internally inconsistent checkpoint records.
- Never mark a source discovered from path existence alone when required identity evidence cannot be read.
- Never advance a checkpoint past unpersisted discovery records.
- A 'gone' TOMBSTONE IS NEVER OUTSTANDING WORK, whatever the corpus set says. A tombstone is excluded, so a reclaimed body is never offered for deletion. The restore case is handled by THE PASS, which re-reads a body that is back and writes a 'restored' record carrying the CURRENT digest - so a source in the set never carries a stale digest. A tombstone is a statement about the PAST and is superseded only by A COMPLETE PASS, so a body restored between two passes - or one a PARTIAL pass never reached - stays invisible until a full pass runs. outstandingSources therefore REFUSES to answer from an incomplete log: the caller must run the pass to completion before asking for the outstanding set.
